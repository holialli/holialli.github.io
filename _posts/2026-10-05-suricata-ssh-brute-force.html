I built a small SOC lab in VirtualBox: Kali as the attacker, Metasploitable2 as the victim, and a third VM running Suricata inline between them, so every packet in either direction passes through the IDS. Suricata writes EVE JSON, Filebeat ships it to Elasticsearch, and I investigate in Kibana. I wrote 30 rules for it, ran Nmap, Hydra and Metasploit from Kali, and watched the alerts come in.

The SSH brute-force rule fired when I ran Hydra against the victim, so I moved on. Coming back to it later, I realised it would also have fired on me logging in once. This post is about why, and what the rule should look like.

What a network IDS can actually see of SSH

SSH encrypts everything after the key exchange, so Suricata never sees a password or a "login failed" message. What it can see is:

  • every TCP connection to port 22, and how often a given source opens them;
  • the version banners both sides send in the clear before encryption starts (SSH-2.0-OpenSSH_…, for example);
  • packet sizes and timing.

So a network rule can't confirm that a password guess failed. It can spot the shape of a brute force: one source opening lots of short connections to SSH. Confirming the failures is the job of the server's own logs (/var/log/auth.log), and in a real SOC you'd correlate the two.

The rule I wrote

alert tcp any any -> 192.168.154.20 22 (msg:"SSH Brute Force";
  threshold:type both, track by_src, count 5, seconds 60;
  classtype:attempted-admin; sid:2000008; rev:1;)

Read it literally: alert when one source sends 5 or more TCP packets to port 22 within 60 seconds. Nothing in it says "connection". Every SYN, ACK, key-exchange message and keystroke counts.

A single normal SSH login sends far more than five packets in its first few seconds: the TCP handshake, the banner exchange, the key exchange, then authentication. So this rule fires on any SSH session at all. It caught Hydra only because Hydra sends packets to port 22, like everyone else.

A detection that fires on both the attack and normal use isn't detecting the attack. Test the negative case too, not just the attack.

Suricata's counting options

Part of the problem was that I didn't fully understand the counting keywords. They behave differently:

KeywordWhat you get
threshold: type thresholdAn alert on every Nth match in the window (count 5 means alerts on the 5th, 10th, 15th…).
threshold: type limitAt most N alerts per window, starting from the first match.
threshold: type bothOne alert per window, once the count is reached. Good for "this source is doing X a lot".
detection_filterSilent until the count is reached, then an alert on every match after that within the window.

type both was the right choice for brute force: an analyst wants one alert per attacker per minute, not hundreds. The mistake was in what was being counted.

Count connection attempts, not packets

Each new TCP connection starts with exactly one SYN from the client, so counting SYNs means counting connection attempts:

alert tcp any any -> $HOME_NET 22 (msg:"LOCAL Possible SSH brute force (5+ new connections from one source in 60s)";
  flags:S,12;
  threshold:type both, track by_src, count 5, seconds 60;
  classtype:attempted-admin; sid:1000008; rev:2;)

What changed and why:

  • flags:S,12 matches packets with only SYN set, ignoring the two ECN bits (CWR and ECE, which is what the 12 means). A SYN-ACK or anything later in the session doesn't match.
  • $HOME_NET instead of a hardcoded victim IP, so the rule follows suricata.yaml. I kept the source as any instead of $EXTERNAL_NET on purpose. $EXTERNAL_NET usually means !$HOME_NET, so in a single-subnet lab like mine, where the attacker sits on the same network as the victim, the rule would never match. And an insider brute-forcing a server is exactly what you want to see anyway.
  • A SID in the 1,000,000 range. My originals used 2,000,000+, which is Emerging Threats' range and can collide if you load ET Open alongside.

The count is a trade-off. OpenSSH allows several password attempts per connection, so a patient attacker can stay under five connections a minute, while automation such as Ansible or a backup script can legitimately open more. For known automation hosts, suppress the rule for that source in threshold.config rather than raising the count for everyone:

suppress gen_id 1, sig_id 1000008, track by_src, ip 10.0.0.5

A second, weaker signal: the client banner

The client's version banner is sent before encryption, and Suricata exposes it as ssh.software. Attack tools are often built on SSH libraries rather than OpenSSH, so the banner can hint at what's connecting. Check your own eve.json to see what your attacker actually sends before relying on it. Legitimate tools use these libraries too, so I'd only use this to add context to the alert above, not as an alert on its own.

Testing rules without re-running the attack

The habit I'd change most is testing. Rather than attacking the lab and watching Kibana, record traffic once and replay it as often as you like:

# 1. Syntax-check the rules
sudo suricata -T -c /etc/suricata/suricata.yaml -S custom.rules

# 2. Record two captures on the IDS: one Hydra run, one normal single login
sudo tcpdump -i eth0 -w hydra.pcap port 22
sudo tcpdump -i eth0 -w normal-login.pcap port 22

# 3. Replay each capture through only your rules and count what fired
suricata -r hydra.pcap -c /etc/suricata/suricata.yaml -S custom.rules -l out-hydra/
jq -r 'select(.event_type=="alert") | .alert.signature' out-hydra/eve.json | sort | uniq -c

-S loads that rules file on its own, so nothing else interferes. The brute-force rule should fire on hydra.pcap and stay silent on normal-login.pcap. The original rule fails the second test, which is the one I never ran.

What I took from it

  • Be precise about what a rule counts. "Five packets" and "five connection attempts" are very different detections.
  • Test the negative case. A rule that fires on the attack proves nothing until you know it stays quiet on normal traffic.
  • Use the network for the pattern and the host for the proof: Suricata sees the connection storm, auth.log sees the failures.
